## 1. 为什么有这一课

第 5 关封板之后复盘，我说了一句：

> "这五关里，有没有哪一关你觉得**当时过了、但心里其实没底**的？"

回答是：

> **"其实我学了这些感觉都没底，因为不知道怎么怎么看日志，而且很懒。"**

这句话里有两件事，都值得认真对待。

### 1.1 "没底"是准的，而且原因很具体

把前五关的验收方式摆出来看：

| 关 | 代码是谁写的 | 谁判断"过了" |
|---|:-:|---|
| 1 话题 | 自己 | 老师（`listener` 改三轮） |
| 2 服务 | 自己 | 老师（老师跑出的 `sum=7`） |
| 3 参数 | 自己 | **老师** ← 自己说过"你帮我测试吧我看结果就行" |
| 4 launch | 自己 | 老师（`colcon test` 老师跑的） |
| 5 动作 | 自己 | 老师（收尾也是老师代跑的） |

**每一关的"通过"，都是别人说了算的。**

> **"底"这个东西不来自"老师批改过了"，只来自"我自己验证过它是对的"。**
>
> 五关里验证权一次都没在自己手上 → **"没底"不是错觉，是精确的自我诊断。**

### 1.2 "不会看日志"和"没底"是同一件事

```
不能自己判断对错  →  卡住只能等  →  等成了常态
```

**这个"等"的体感，很容易被翻译成"我很懒"。但它其实是"我不知道该看哪儿"。**

（真要论"懒"：把 VSCode 全部自动补全关掉是**自己提的**，没人要求。那意味着每个字符都是从零敲出来的。**懒人不会给自己加这道刑。**）

### 1.3 这一课要解决什么

**不是教你"读代码"——是教你"读症状"。**

```
以前：代码不对 → 猜哪里错了 → 改 → 再猜        （猜是运气）
现在：代码不对 → 描述症状   → 定位 → 改        （对表是能力）
```

## 2. 核心概念

### 2.1 ⭐ 日志里只有两种行

| | 是什么 | 例子 | 怎么办 |
|---|---|---|---|
| **仪式行** | 每个 ROS 程序都有，**跟你的逻辑一点关系没有** | `[INFO] [1789480363.254] [fib_server]:` 这个前缀本身、中间件偶尔打的字 | 大部分时候**直接无视** |
| **业务行** | **你自己写的 `get_logger().info(...)`** | `收到进度(3)：array('i', [0, 1, 1, 2, 3])` | **只有它们能告诉你程序走到哪了** |

> **看日志的第一步，就是把业务行挑出来单独看。**

挑法很简单——**按节点名过滤**（见 §6）：

```bash
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | cat -n
```

### 2.2 ⭐⭐ 看日志 = 预期 − 实际

**看出来问题的能力，等于"你以为会发生的"减去"实际发生的"。差在哪，问题就在哪。**

这个减法要能做，前提是**你脑子里得有"预期"**。

**这就是为什么本课一路强调"先预测、再运行"**——那个动作不是走流程，**它就是在造"预期"**。

没有预期的人看日志，就像没有原图的人玩"找不同"：他一眼扫过去，觉得"挺正常的啊"。

### 2.3 报错的有无，三种情况

第 4 关已经见过这三种，本课再强化一次：

| | 情况 | 例子 |
|---|---|---|
| ① | **不报错，但真错了**（最难抓） | `glob` 静默返回 `[]`；`CMakeLists` 漏 `add_executable`；本课 L3 的数值错误 |
| ② | **报了错，但真没错**（最容易吓到自己） | VSCode IntelliSense 假红线；`ros2 action send_goal` 取消时的 `Executor is already spinning` |
| ③ | 报错且真错了（正常情况） | 绝大多数 `AttributeError` / `TypeError` |

> **永远以实测为准，别拿"有没有报错"当结论。**

### 2.4 ⭐ 三层防线，从外到内

本课三轮训练，正好对应越来越深的三层：

```
第 1 层  行数     —— 打印了几行？                    （L1）
第 2 层  内容     —— 每一行是什么？                   （L2）
第 3 层  数值     —— 内容里的数字对不对？              （L3）
```

**越往里越难抓，因为外面几层全是"正常"的。**

L3 那个 bug：**行数对、状态对、没报错——三条防线全部通过，只有数组里的数字是错的。**

> **如果检查只做到"跑通了吗"，这个 bug 能一路走到用户手里。**

## 3. 方法：对表法

### 3.1 怎么做

**拿一份"正常"的输出当表格，把出问题的输出逐行对照，打勾打叉。**

```
服务端行数      3    ==  正常 3         ✓
客户端行数      9    ==  正常 9         ✓
最终状态        5    ==  正常 5         ✓
有没有报错      没有  ==  正常没有       ✓
──────────────────────────────────────
收到进度(1)   [0,1,2]  vs  正常 [0,1,1]      ✗  ← 就这一个
```

**剩下的那个 ✗，就是症状。**

### 3.2 为什么它有用

**因为它是纯客观的，一个字都不用懂代码。**

看不懂 `feedback_msg.sequence.append(...)` 没关系。你只要能把两份输出摆在一起，就能说出"只有数值不对"。

**先打到这一步，再去看代码。** 顺序反了就会瞎猜。

### 3.3 ⭐ "正常"从哪来

**平时就要攒。**

跑通一个程序之后，**顺手把输出贴进一个文件存着**：

```bash
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n > ~/normal_fib_client.txt
```

以后出问题，`diff` 一下：

```bash
diff ~/normal_fib_client.txt <(ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n)
```

> **`diff` 就是"对表法"的自动化版本。**
> **`预期 − 实际` 这个减法，机器一秒就能做完——前提是你存过"预期"。**
>
> ⚠️ **那个 `sed` 是为了剥掉时间戳**，不然每次跑都不同，`diff` 会把每一行都报成差异。详见 §6.1。

## 4. 最重要的一条：先描述，再解释

### 4.1 两个问题，别混

| | 问题 | 需要什么 | 输出 |
|---|---|---|---|
| **①** | **哪里不对？** | **不需要懂代码**，只要对比两份输出 | 症状描述 |
| **②** | **为什么不对？** | 才需要看代码、猜逻辑 | 原因假设 |

**顺序不能反。**

### 4.2 反面教材（本课真实发生）

L3 里我问了这两个问题，回答是：

> 「应该是把前面所有数加起来再加1，我觉得大概率是 feedback 循环的问题」

**这答的是 ②，① 跳过了。** 而且追问之后，**又跳过了一次**。

### 4.3 跳步的代价

跳过 ① 直接猜 ②，猜中的概率很低。真实的历史记录：

| 关 | 猜的 | 实际的 |
|---|---|---|
| 2 | 把 `a=3`、`b=4` 塞进了 `request` | 参数名对不上 → 静默算出 `sum=0` |
| 4 | `glob` 连改三版，**每次都在改右边** | 左边缺了 `launch/` 那一截 |
| 5 | `goal_handle.cancel_call` | 真名是 `is_cancel_requested` |

> **共同点：还没搞清楚"哪里不对"，就开始改。改的是猜的地方，不是坏的地方。**

### 4.4 ① 的标准答法

**只描述观察，不解释原因：**

> ✅ "行数、状态、取消全跟正常一样，也没报错——**只有 `收到进度` 里的数组数值不对**。"

对比一下：

> ❌ "应该是循环里的加法写错了。" —— 这是 ②，而且可能是错的。

## 5. 实战：三轮训练 ⭐

三轮全部用**已经跑通的 `fib_server` / `fib_client`**，不引入任何新概念。
规则：**先预测 → 再运行 → 对表 → 找差异。**

### 5.0 基准：正常长什么样（L1 用它当标准答案）

**服务端（3 行）**

```
1  收到目标：order=30
2  收到取消请求
3  目标被取消
```

**客户端（9 行）**

```
1  等待动作服务端...
2  发送目标：order=30
3  目标被接受，开始等结果
4  收到进度(1)：array('i', [0, 1, 1])
5  收到进度(2)：array('i', [0, 1, 1, 2])
6  收到进度(3)：array('i', [0, 1, 1, 2, 3])
7  >>> 够了，我要叫停
8  最终结果：array('i', [0, 1, 1, 2, 3])
9  最终状态：5
```

**时间**：服务端收到目标 → 收到取消请求，间隔 **2 秒**；取消请求 → 目标被取消，间隔 **1 秒**。全程约 **3 秒**。

> **这份输出就是"底"。存着。**

---

### 5.1 L1：数行数

**题目**：不跑，先预测——两个终端各打印几行？什么顺序？服务端最后一行是什么？

**作答**：① 3 / ② 8 / ③ 3 / ④ `result.sequence` → **实际 ① 3 ✅ ② 9 ❌ ③ 3 ✅ ④ `目标被取消` ❌ → 3/4**

#### ❌ 错法一：数的是**源文件行数**，不是**打印行数**

`fib_client.py` 里只有 **8 个** `get_logger().info`，但实际打印了 **9 行**：

```
等待动作服务端...          ← 1
发送目标：order=30         ← 2
目标被接受，开始等结果      ← 3
收到进度(1)：...           ← 4  ┐
收到进度(2)：...           ← 5  ├ 源文件里是【同一行】，
收到进度(3)：...           ← 6  ┘ 但它在循环里，打了 3 次
>>> 够了，我要叫停         ← 7
最终结果：array(...)       ← 8
最终状态：5                ← 9
```

> **数"源文件里几行代码"和数"实际打印几行"，是两个数。**
>
> 这跟 `goal_handle` vs `goal_handle.request`、`feedback_msg` vs `feedback_msg.sequence` **是同一个形状**：
> **你看着的那个东西，和你以为它代表的东西，不是一回事。**

#### ❌ 错法二：服务端 / 客户端串门

④ 答成了 `result.sequence`（第 50 行，**成功分支**的返回值）。追问后又答 "5"。

**而 5 是客户端第 9 行 `最终状态：5` 里的那个数字。**

> 服务端最后一行的答案是 **`目标被取消`**——
> **因为客户端取消了，成功那条路根本没走到。**
>
> **代码里有这条路，不代表这次会走这条路。**

#### ⭐ 而且：① 和 ④ 是自相矛盾的

服务端一共 3 行，④ 却答了一个**不在这 3 行里**的东西。

> **用自己已经写下的答案去卡自己** —— 这个检查零成本、不用打字、不用问人。
> 本课里它出现了**两次**，两次都是没回头对一眼。

---

### 5.2 L2：行数一样，内容全变

**改动**（`cancel_callback` 里，只改一个词）：

```python
return CancelResponse.ACCEPT     # 原版
return CancelResponse.REJECT     # 改坏
```

**预测**：① 服务端几行 + 末行 ② 客户端末行的数字 ③ `收到进度` 打到几号
**作答**：① 3 行 / 返回结果 ② 4 ③ 29 → **3/3 全对** ✅

> ③ 是**推出来的**：`order=30` → `range(1, 30)` 跑 **29** 次。
> 用的正是 L1 学到的那件事——**打印行数 ≠ 源文件行数**。

**实际结果**：

| | 正常 | 改坏 |
|---|---|---|
| **服务端行数** | 3 | **3（没变！）** |
| 客户端行数 | 9 | **35** |
| 最终状态 | 5 | **4** |
| 取消后还要等 | 1 秒 | **27 秒** |

**服务端逐行对比**：

```
正常版                  改坏版
─────────────          ─────────────
1 收到目标：order=30     1 收到目标：order=30
2 收到取消请求           2 收到取消请求
3 目标被取消   ←        3 返回结果：array(...)   ←
```

#### ⭐ 结论一：行数一模一样，第 3 行完全是另一个东西

> 上一轮刚学会"**数行数**"。这一轮的陷阱正好是：**行数对了，不代表对了。**

#### ⭐ 结论二：症状和病根不在同一个地方

**症状全在客户端（9 → 35 行），病根是服务端的一个词。**

#### ⭐ 结论三：`收到取消请求` 照样打印了

```
"我收到了请求"  ≠  "我答应了"  ≠  "取消生效了"
```

**一行日志只证明了第一件事。**

---

### 5.3 L3：三条防线全过，只有数值错

**改动**（**不告诉改了哪**，从日志反推）：

```python
feedback_msg.sequence.append(
    feedback_msg.sequence[i] + feedback_msg.sequence[i - 1])   # 原版

feedback_msg.sequence.append(feedback_msg.sequence[i] * 2)     # 改坏
```

**实际结果**：

**服务端（3 行）——完全正常**

```
1  收到目标：order=30
2  收到取消请求
3  目标被取消
```

**客户端（9 行）——行数正常、状态正常、没报错**

```
1  等待动作服务端...
2  发送目标：order=30
3  目标被接受，开始等结果
4  收到进度(1)：array('i', [0, 1, 2])          ← 正常是 [0, 1, 1]
5  收到进度(2)：array('i', [0, 1, 2, 4])       ← 正常是 [0, 1, 1, 2]
6  收到进度(3)：array('i', [0, 1, 2, 4, 8])    ← 正常是 [0, 1, 1, 2, 3]
7  >>> 够了，我要叫停
8  最终结果：array('i', [0, 1, 2, 4, 8])
9  最终状态：5                                  ← 正常
```

#### 作答

- **② 定位：完全正确** —— 就是 `feedback_msg.sequence.append(...)` 那两行。
- **① 症状：连续跳过两次** —— 问"哪里不对"，两次都答"我猜在哪里"。
  用填四个空逼着走完一次后，答对了：

> **"行数正确，状态正确，报错正确，只有数值不对。"**

#### ⭐ 结论一：这是最难抓的一类 bug

```
行数   ✓        状态   ✓        报错   ✓        数值   ✗
```

**三条防线全部通过。**

#### ⭐ 结论二：症状相符 ≠ 病因相符

当时猜的公式是「前面所有数加起来再加 1」。**它跟实际的 `× 2` 产生的数列一模一样**：

```
[0, 1]  →  求和 1，+1 = 2      ×2 = 2
[0, 1, 2]  →  求和 3，+1 = 4      ×2 = 4
[0, 1, 2, 4]  →  求和 7，+1 = 8      ×2 = 8
```

> 在这个特定序列下，两个公式**数值完全等价**。
>
> **所以从输出反推代码，你可能推到一个数值相同的错误公式。**
> **这就是 ① 和 ② 必须分开做的原因：① 是客观的，② 是猜测。**

#### ⭐ 结论三：能发现它，靠的是"知道斐波那契应该是 0,1,1,2,3"

**没有任何一行日志会告诉你"算错了"。** 日志只说"我算出来是 `[0,1,2,4,8]`"。

**是你脑子里的"预期"在报警。**

> **这就是"底"的来源：知道正常该是什么样。**

---

### 5.4 三轮总结

| | 考的是 | 结果 |
|---|---|---|
| **L1** | 行数 | 3/4 |
| **L2** | 内容 | **3/3** |
| **L3** | 数值 | 定位精确，① 补上 |

**难度一路加，表现一路涨。**

## 6. 工具速查

### 6.1 ⭐ 只挑业务行 + 剥前缀 + 编号

```bash
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n
```

三步，各干一件事：

| 命令 | 干什么 | 为什么 |
|---|---|---|
| `grep '\[fib_client\]'` | **挑业务行** | 按节点名过滤，仪式行全扔掉 |
| `sed -E 's/^.*\]: //'` | **剥掉前缀** | ⚠️ **`[INFO] [时间戳] [节点名]:` 里有时间戳，每次跑都不一样** |
| `cat -n` | **编号** | 一共有几行，一眼就看见 |

**服务端同理**（把 `fib_client` 换成 `fib_server`）：

```bash
ros2 run hello_ros fib_server 2>&1 | grep '\[fib_server\]' | sed -E 's/^.*\]: //' | cat -n
```

> **为什么按 `[节点名]` 过滤？** 因为 rclpy 的每条日志都带这个前缀：
> `[INFO] [1789480363.254433981] [fib_server]: 收到目标：order=30`
> 有了它，**你完全不用管"这行是谁打的"**。

> ⚠️ **那个 `sed` 不能省。**
> 剥完之后，剩下的**只有你的消息本身**——`收到进度(2)：array('i', [0, 1, 1, 2])`。
> **这时候两份输出才可比。** 不剥的话，时间戳会把每一行都变成"差异"。

### 6.2 存一份"正常"下来

```bash
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n > ~/normal_fib_client.txt
```

### 6.3 ⭐ 用 `diff` 自动对表

```bash
diff ~/normal_fib_client.txt <(ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n)
```

**没输出 = 完全一样。有输出 = 差异就在那几行。**

**实测（本课验证过）**：同一个正常服务端跑两次 → **无输出** ✓

拿 L3 那个 `×2` 的改坏版对比 → **正好报出 4 行，而且全是数值行**：

```
4,6c4,6
<      4	收到进度(1)：array('i', [0, 1, 1])
<      5	收到进度(2)：array('i', [0, 1, 1, 2])
<      6	收到进度(3)：array('i', [0, 1, 1, 2, 3])
---
>      4	收到进度(1)：array('i', [0, 1, 2])
>      5	收到进度(2)：array('i', [0, 1, 2, 4])
>      6	收到进度(3)：array('i', [0, 1, 2, 4, 8])
8c8
<      8	最终结果：array('i', [0, 1, 1, 2, 3])
---
>      8	最终结果：array('i', [0, 1, 2, 4, 8])
```

> **注意：行数、顺序、"够了我要叫停"、`最终状态：5`——一条都没报。**
> **`diff` 把噪音全滤掉了，只把"真正不一样的地方"摆到你面前。**
>
> **这就是"对表法"的自动化版本——而且是免费的。**

### 6.4 跑之前先清残留（⚠️ 很重要）

**用 `ros2 run` 起的**（你平时那种）：

```bash
pkill -f fib_server; sleep 1; ps -eo pid,etimes,args | grep fib_server | grep -v grep
```

**没输出 = 干净。**

> ⚠️⚠️ **但 `pkill -f fib_server` 只对"命令行里真的写着 `fib_server`"的进程有效。**
>
> `pkill -f` / `pgrep -f` 匹配的是**命令行文本**，**不是节点名**。所以：
>
> | 你怎么起的 | 命令行长什么样 | `pkill -f fib_server` 有效吗 |
> |---|---|---|
> | `ros2 run hello_ros fib_server` | `.../install/hello_ros/lib/hello_ros/fib_server` | ✅ 有效 |
> | `python3 /tmp/my_server.py` | `python3 /tmp/my_server.py` | ❌ **完全无效** |
>
> **第二种情况要按脚本名查**：
>
> ```bash
> ps -eo pid,etimes,args | grep -E 'python3 /tmp/.*\.py' | grep -v grep
> ```
>
> 加了 `etimes`（活了多久）更好判断——**跑了几百秒的一定是残留，正常测试只要几秒。**

**为什么必须先做这一步**：如果有一个旧的服务端还活着，**两个服务端会同时提供同一个动作名**，客户端收到的进度是**两个服务端交错的**——数值看着莫名其妙，你会以为自己代码写错了。

**见 §7.1** —— 这是真实踩过**两次**的坑，第二次连"正常基准"都被污染了。

### 6.5 看有没有报错

```bash
grep -nE 'Traceback|ERROR|Exception' 你的日志文件
```

**想要一份日志干净，先确认这条命令没有输出。**

## 7. 踩坑记录

### ⚠️⚠️ 坑 1：残留进程让日志变成垃圾（本课造题时**真实踩了两次**）

#### 症状

造 L3 那道题时，第一次跑出来的数值是这样的：

```
收到进度(1)：array('i', [0, 1, 1])
收到进度(2)：array('i', [0, 1, 2])
收到进度(3)：array('i', [0, 1, 1, 2])
```

**看着完全像"代码坏了"。实际上：**

```
收到进度(1) [0,1,1]      ← 旧服务端（正常版）
收到进度(2) [0,1,2]      ← 新服务端（改坏版）
收到进度(3) [0,1,1,2]    ← 旧服务端
```

**两个服务端同时提供 `/fibonacci`，客户端收到的进度是它们交错的。**

**为什么会交错？** 动作名是**共享**的——DDS 按名字匹配，**它不知道你有几个服务端**。两个都算，客户端谁的消息先到就收谁的。

#### 更阴的一次：连"正常"基准都被污染了

第二次踩，是验证 `diff` 那条命令的时候。跑"正常版"存基准，存出来的文件长这样：

```
1  等待动作服务端...
2  发送目标：order=30
3  目标被接受，开始等结果
4  收到进度(1)：array('i', [0, 1, 2])      ← 改坏版的值！
5  收到进度(2)：array('i', [0, 1, 1])      ← 正常版的值
6  收到进度(3)：array('i', [0, 1, 2, 4])   ← 改坏版的值
```

**"正常"基准本身是脏的。用这种基准去 `diff`，等于拿一把坏尺子量东西。**

#### ⭐ 真凶：`pkill -f` 杀不掉它

**关键认知：`pkill -f <pattern>` 匹配的是「命令行文本」，不是「节点名」。**

```
进程的节点名（代码里写的）     →  fib_server
进程的命令行（ps 看到的）      →  python3 /tmp/l5_mystery_server.py
                                    ↑ 这里面根本没有 "fib_server"
```

**所以 `pkill -f fib_server` 对它完全无效**——我杀了半天，一个都没杀掉，还以为"干净了"。

**甚至连探针都是坏的**：我写了个 `pgrep -af fib_server` 当探针，它**每次返回空**——不是我清得干净，是**这把尺子根本量不到那个东西**。

> **这是本课最值钱的一条：你以为你在验证，其实你的验证工具本身就坏了。**
> **"干净了"和"探针返回空"是两回事。**

#### ⭐ 另一个来源：脚本自杀，留下孤儿

还有一次残留是这么来的——一个测试脚本开头写了 `pkill -f 'fib[_]server'`，**结果自匹配把自己杀了**（见坑 2），**死在后面那句 `kill $服务器PID` 之前**。

于是它启动的服务端成了**孤儿进程**，在后台活了 **570 秒**，污染了后面每一次测试。

> **教训：会自杀的脚本，一定会留孤儿。**

#### ✅ 正确做法

**① 按「你启动它的方式」去查，不是按节点名。**

```bash
ps -eo pid,etimes,args | grep -E 'l5_[a-z_]*\.py' | grep -v grep
```

- `ps -eo pid,etimes,args` —— **`etimes` 是"已经活了多久（秒）"**。这个数字特别有用：**跑了几百秒的，一定是上一次的残留**，因为正常一次测试只要几秒。
- 正则匹配的是**你启动它的那条命令行**。
- **`grep -v grep`** —— 不然 grep 自己那一行也会被列出来。

**② 杀完之后，用 `ps` 复查**（不要假设它死了）：

```bash
kill <PID>; sleep 2; ps -p <PID> || echo "已死"
```

**③ 只要症状是"数值莫名其妙"，第一件事就是查残留。**

#### 这跟第 3 关的旧账是同一类

那次是 `pkill` 之后 `/dev/shm` 留了垃圾，导致 `[RTPS_TRANSPORT_SHM Error]`。

**共同点：环境不干净，症状却长在代码身上。**

> **跑任何"服务端 + 客户端"之前，先确认没有旧的服务端活着。**
> **而且"确认"要用对尺子。**

### ⚠️ 坑 2：`pkill -f fib_server` 会**杀掉自己**

```bash
pkill -f fib_server        # ✗ 把跑这条命令的 shell 也杀了
```

因为 `pkill -f` 匹配的是**整条命令行**，而你这条命令行里**就写着 `fib_server`**。

**同样的坑**：`pkill -f 'fib[_]server'` 也不行——只要你的命令行里**别处**出现了 `fib_server`（比如后面跟了个 `grep '\[fib_server\]'`），照样自匹配。

**修法：让那个字符串在命令行里不连续出现。**

```bash
P="fib""_server"; pkill -f "$P"
```

`"fib""_server"` 拼起来是 `fib_server`，但**命令行里的字面量是 `fib""_server`**，匹配不上自己。

> 💡 **在交互式终端里手敲 `pkill -f fib_server` 通常是安全的**（shell 的命令行只有 `-bash`）。
> 这个坑主要在**脚本 / 一行式命令**里发作。

#### ⚠️ 连带后果：**会自杀的脚本，一定会留孤儿**

这个坑最坏的地方不是"脚本死了"，是**脚本死在哪一行**。

真实案例：某个测试脚本长这样——

```bash
pkill -f 'fib[_]server'        # ← 自匹配，脚本在这里被自己杀死 ✗
sleep 2
python3 /tmp/my_server.py &
SRV=$!
...
kill "$SRV"                    # ← 永远执行不到
```

**脚本死在半路，它启动的服务端就成了孤儿**，在后台活了 **570 秒**，污染了后面每一次测试（见 §7.1）。

> **修法：把清残留放在脚本**外面**先手动做，别让脚本自己"边清边跑"。**
> 或者至少把 `pkill` 放在所有 `&` 之后，保证自杀也不会留下已经启动的东西。

### ⚠️ 坑 3：`kill` 拆台时留下的 Traceback 不是 bug

测试脚本最后 `kill` 服务端时，日志里会多出这么一段：

```
rclpy._rclpy_pybind11.RCLError: failed to initialize wait set:
the given context is not valid, either rcl_init() was not called
or rcl_shutdown() was called.
```

**这是我用 `kill` 强制关停、正好撞上 `spin` 循环造成的，跟被测试的代码无关。**

> **别看到 Traceback 就以为是自己错了。** 第 4 关的"VSCode 假红线"、第 5 关的 `Executor is already spinning` 都是同一类。

## 8. 自测题

### 8.1 课堂已覆盖（附答案）

<details>
<summary><b>题 1：日志里的"仪式行"和"业务行"分别是什么？</b></summary>

- **仪式行** —— 每个 ROS 程序都有、跟你的逻辑无关的行。比如 `[INFO] [时间戳] [节点名]:` 这个前缀本身。
- **业务行** —— 你自己写的 `get_logger().info(...)`。**只有它们能告诉你程序走到哪了。**

**看日志的第一步，就是把业务行挑出来单独看**：

```bash
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | cat -n
```
</details>

<details>
<summary><b>题 2：<code>fib_client.py</code> 里有 8 个 <code>get_logger().info</code>，为什么实际打印 9 行？</b></summary>

因为 `收到进度(N)：...` 那一行**在 `feedback_callback` 里**，每收到一次进度就执行一次。这次收到了 3 条 → 那一行代码打印了 3 次。

**8 行代码 − 1（`目标被拒绝` 没走）+ 3（`收到进度` 打了 3 次）− 1 = 9。**

> **数"源文件里几行代码"和数"实际打印几行"，是两个数。**
</details>

<details>
<summary><b>题 3：把 <code>CancelResponse.ACCEPT</code> 改成 <code>REJECT</code>，服务端还是 3 行吗？</b></summary>

**是，还是 3 行**——但第 3 行换了：

```
正常版                  改坏版
1 收到目标：order=30     1 收到目标：order=30
2 收到取消请求           2 收到取消请求
3 目标被取消             3 返回结果：array(...)
```

**行数一模一样，第 3 行完全是另一个东西。**

> 这题专门用来打破"数行数就够了"的错觉。**行数对了，不代表对了。**
</details>

<details>
<summary><b>题 4：为什么取消被拒绝时，<code>收到取消请求</code>还是会打印？</b></summary>

因为 `cancel_callback` **被调用了**——它只是**返回了 `REJECT`**。日志打在 callback 里，callback 一执行就打印。

**三件事要分清楚：**

```
"我收到了请求"  ≠  "我答应了"  ≠  "取消生效了"
    ↑              ↑                ↑
 收到取消请求    ACCEPT/REJECT    服务端真的停下来
```

**一行日志只证明了第一件事。**
</details>

<details>
<summary><b>题 5：L3 那个 bug，为什么说它"最难抓"？</b></summary>

因为**三层防线全部通过**：

```
行数   ✓   （服务端 3 行、客户端 9 行，跟正常一样）
状态   ✓   （最终状态 5，跟正常一样）
报错   ✓   （一个 Traceback 都没有）
数值   ✗   （[0,1,2,4,8] 而不是 [0,1,1,2,3]）
```

而且**没有任何一行日志会告诉你"算错了"**——日志只说"我算出来是 `[0,1,2,4,8]`"。

**能发现它，靠的是你脑子里的"预期"（斐波那契应该是 0,1,1,2,3）。**

> **如果检查只做到"跑通了吗"，这个 bug 能一路走到用户手里。**
</details>

<details>
<summary><b>题 6：「哪里不对」和「为什么不对」，为什么要分开？</b></summary>

| | 需要什么 | 输出 |
|---|---|---|
| **① 哪里不对** | **不需要懂代码**，只对比两份输出 | 症状 |
| **② 为什么不对** | 才需要看代码、猜逻辑 | 原因假设 |

**顺序不能反。** 因为 ② 是猜测，猜中的概率很低；而 ① 是客观的，人人都能做。

跳过 ① 直接猜 ② 的历史记录：第 2 关把 `a=3`/`b=4` 塞进 request（实际是参数名对不上，静默算出 `sum=0`）、第 4 关 `glob` 连改三版都在改右边（实际是左边缺了 `launch/`）、第 5 关猜 `goal_handle.cancel_call`（真名是 `is_cancel_requested`）。

> **共同点：还没搞清楚"哪里不对"，就开始改。改的是猜的地方，不是坏的地方。**
</details>

<details>
<summary><b>题 7：为什么"从输出反推代码"可能推出一个错误的公式？</b></summary>

因为**不同的公式可能产生完全一样的输出**。

L3 那个改动是 `sequence[i] * 2`，但当时猜的是「前面所有数加起来再加 1」：

```
[0, 1]     →  求和 1，+1 = 2      ×2 = 2      ← 一样
[0, 1, 2]  →  求和 3，+1 = 4      ×2 = 4      ← 一样
```

**在这个特定序列下，两个公式数值完全等价。**

> **症状相符 ≠ 病因相符。**
> 这就是为什么 ①（描述）和 ②（解释）必须分开做——**① 是客观的，② 是猜测。**
</details>

<details>
<summary><b>题 8：跑"服务端 + 客户端"之前，为什么必须先确认没有旧的服务端活着？</b></summary>

因为**两个服务端会同时抢同一个动作名**。客户端收到的进度是**两个服务端交错的**：

```
收到进度(1) [0,1,1]      ← 旧服务端（正常版）
收到进度(2) [0,1,2]      ← 新服务端（改坏版）
收到进度(3) [0,1,1,2]    ← 旧服务端
```

**这看起来完全像"代码坏了"，但其实是环境污染。**

查法：`pgrep -af fib_server`（没输出才干净）。

> 这跟第 3 关 `pkill` 之后 `/dev/shm` 留垃圾导致 `[RTPS_TRANSPORT_SHM Error]` 是同一类问题。
</details>

<details>
<summary><b>题 9：<code>pkill -f fib_server</code> 为什么杀不掉 <code>python3 /tmp/my_server.py</code>？该怎么查？</b></summary>

**因为 `pkill -f` / `pgrep -f` 匹配的是「命令行文本」，不是「节点名」。**

```
节点名（代码里写的）     →  fib_server
命令行（ps 看到的）      →  python3 /tmp/my_server.py
                              ↑ 这里根本没有 "fib_server"
```

**匹配不上，所以杀不掉。**

**正确的查法：按"你启动它的方式"去查。**

```bash
ps -eo pid,etimes,args | grep -E 'python3 /tmp/.*\.py' | grep -v grep
```

`etimes` 是"活了多久（秒）"——**正常一次测试只要几秒，跑了几百秒的一定是残留。**

> ⭐ **更狠的一层**：如果拿 `pgrep -af fib_server` 当"查残留"的**探针**，它会**每次返回空**。
> 你会以为"干净了"，**其实是尺子量不到那个东西。**
>
> **"干净了"和"探针返回空"是两回事。**
</details>

### 8.2 留给下次的思考题（无答案）

1. **`diff` 的局限在哪？** 如果改动只影响**时间戳**、或者只影响**行内某几个字符**，`diff` 会怎么报？用它做"对表"可靠吗？
2. **如果要给 `fib_server` 加一条"每算一项打印一次当前索引"的日志**，L3 那个数值 bug 会不会变得更容易发现？**加日志时你会加什么？**（提示：想想"什么信息能让你一眼看出算错了"。）
3. **现在只有 `info` 一种级别。** `get_logger().warn(...)` / `.error(...)` 除了字面上的区别，**在命令行和工具里还有什么不一样？**（试试 `ros2 run ... --ros-args --log-level warn`。）
4. **"正常运行"的输出** 和 **"边界情况"的输出**（`order=1`、`order=0`、连续发两个目标）你能预期吗？**先写预测，再跑。**
5. **服务端和客户端的时间戳能对上吗？** 拿 L1 那份带时间戳的原始日志（不是 `grep` 过滤后的），**算一下"客户端发出取消"到"服务端响应取消"差了几毫秒**，跟第 5 关笔记 §7.3 的数字对不对得上。

## 9. 附：速记卡

```bash
# ---------- 只挑业务行 + 剥前缀 + 编号 ----------
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n
ros2 run hello_ros fib_server 2>&1 | grep '\[fib_server\]' | sed -E 's/^.*\]: //' | cat -n
#                                     ↑ 挑业务行          ↑ 剥掉[INFO][时间戳]前缀（不能省）    ↑ 编号

# ---------- 存一份"正常" ----------
ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n > ~/normal_fib_client.txt

# ---------- 自动对表 ----------
diff ~/normal_fib_client.txt <(ros2 run hello_ros fib_client 2>&1 | grep '\[fib_client\]' | sed -E 's/^.*\]: //' | cat -n)

# ---------- 跑之前清残留（重要） ----------
pkill -f fib_server; sleep 1; ps -eo pid,etimes,args | grep fib_server | grep -v grep
#                                          ↑ etimes = 活了多久。几百秒的一定是残留

# ---------- 万能版：按"你启动它的方式"查 ----------
ps -eo pid,etimes,args | grep -E 'python3 /tmp/.*\.py' | grep -v grep

# ---------- 杀完要复查，别假设它死了 ----------
kill <PID>; sleep 2; ps -p <PID> || echo "已死"

# ---------- 看有没有报错 ----------
grep -nE 'Traceback|ERROR|Exception' 你的日志文件
```

**五条口诀**

```
① 先挑业务行，无视仪式行
② 看日志 = 预期 − 实际
③ 行数对、状态对、没报错 ≠ 对
④ 先描述，再解释 —— 顺序不能反
⑤ 别猜，去测 —— 但先确认你的尺子没坏
```

> 第 ⑤ 条是血换来的：本课造题时，我拿 `pgrep -af fib_server` 当"查残留"的探针，
> 它**每次都返回空**——我当时以为"干净了"，
> **其实是那个进程的命令行里根本没有 `fib_server` 这个词，尺子量不到它。**
>
> **"干净了"和"探针返回空"是两回事。**

**三层防线（越往里越难抓）**

```
第 1 层  行数    →  打印了几行？
第 2 层  内容    →  每一行是什么？
第 3 层  数值    →  内容里的数字对不对？
```
