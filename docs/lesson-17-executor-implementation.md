# 第 17 关 · 换个执行器（顺序长在名单上，还是长在发名单的人身上？）

> **进度：已完成（2026-10-09）。** 实验全部跑完，§1–§10 已补。
>
> ⭐ **一句话**：**「从尾巴取」是【发名单的人】的性质。**
> 名单一个字没改，换个人来发，指的方向就变了 —— 而且从「**确定**」变成了「**抢**」。
>
> 第 16 关把「谁先上」算出来了，答案由**两个零件**拼成：
>
> | 零件 | 第 16 关怎么拿到的 | 原话 |
> |---|---|---|
> | ① **名单**按**地址升序**排 | **读出来的**（`std::set` + `owner_less`，源码在本机） | 板上钉钉 |
> | ② 执行器**从名单的尾巴**那头发 | ⚠️ **推出来的**（本机只装了头文件，执行器的 `.cpp` 读不到） | 自己打了标 |
>
> 然后它把这两条合起来，写成一句话：
>
> > `B` 的地址最大（它是后建的）⇒ 执行器从名单【尾巴】那头发 ⇒ **`B` 先上**。
>
> ⚠️ 第 16 关在收官时自己承认了两件事：
> **② 是推的不是读的**，而且**「去找真正的 `.cpp`」这条路已经堵死**（它 §2.6 当场翻的）。
>
> 本关不再往下拆零件 —— **本关把整个「发名单的人」换掉。**
>
> ⭐ 第 12 关那句「换容器 = 换执行器」其实只换了**参数**（几条手），
> 用的还是**同一个类**。**本关是第一次换【实现】—— 换一个别的类来当执行器。**
>
> 于是 ① 和 ② 被硬生生拆开了：
>
> | | 是什么 | 换执行器之后 |
> |---|---|---|
> | ① 名单长什么样 | **数据** | 还在（名单是别处造的） |
> | ② 怎么走这份名单 | **行为** | **换人了** |
>
> **只拧这一个旋钮**，就能问出那句一直没被问过的话：
> **「谁先上」这件事，到底归谁管？**

### 0.1 这一关要回答的问题

1. 第 16 关的答案有两个零件：**名单**（按地址排）和 **从尾巴取**。

2. 换一个执行器实现（**代码一个字不改**），先上比例会变成多少？

4. `--isolated` 打开后，**手数**（第 12 关那把尺子）会不会变？**由什么决定？**

### 0.2 理论背景（答题时边答边翻）

#### (a) 「执行器」这个词，前十六关出现过**两种**意思

| 出处 | 换的是什么 | 类比 |
|---|---|---|
| 第 12 关：「换容器 = 换执行器」 | 换**配置**（几条手、单线程/多线程）—— **同一个类** | 同一台机器**调档位** |
| **第 17 关** | 换**类本身** —— 换一整台**机器** | **换一台别的机器** |

⭐ 一句话：**前十六关从头到尾只见过一个执行器，只是把它的档位拧来拧去。**

#### (b) 三个执行器实现（都住在同一片头文件目录里）

| 名字（英文我翻好） | 头文件（本机上都有） | 谁在用它 |
|---|---|---|
| `SingleThreadedExecutor`（单线程执行器） | `executors/single_threaded_executor.hpp` | `--executor-type single-threaded`（容器的**默认**） |
| `MultiThreadedExecutor`（多线程执行器） | `executors/multi_threaded_executor.hpp` | `--executor-type multi-threaded`（**第 12–16 关一直用的**） |
| `EventsCBGExecutor`（事件 / 回调组执行器） | `executors/events_cbg_executor/events_cbg_executor.hpp` | 🆕 `--executor-type events-cbg`（**本关**） |

三个都是 `rclcpp::Executor` 的**派生类**（基类在 `rclcpp/executor.hpp:64`）。

⚠️ 名字里那两个词先翻译好：

| 英文 | 中文 | 记忆点 |
|---|---|---|
| event | 事件 | 「**有事发生了**」的一条通知 |
| CBG = callback group | 回调组 | 第 13 关那格 |
| scheduler | 调度器 | **自己排班**，不排队等人来问 |

#### (c) ⭐ 两份「名单」，两个**不一样**的容器（本关的题眼就在这张表）

| 名单在谁手里 | 出处（本机源码） | 容器 | 这个容器**天然**给的顺序 |
|---|---|---|---|
| **基类** `Executor` 的收集器 | `executors/executor_entities_collector.hpp:157-159` | `std::set` + `owner_less` | **地址从小到大** ← 第 16 关读的就是这份 |
| **本关这个执行器**自己的 | `executors/events_cbg_executor/events_cbg_executor.hpp:303` | `std::vector` | **加入的先后** |
| 同一份，第二处 | `executors/events_cbg_executor/events_cbg_executor.hpp:310` | `std::vector<CallbackGroupData>` | **加入的先后** |
| （旧账）**节点**自己手里那份 | `node_interfaces/node_base.hpp:154` | `std::vector` | **创建顺序** |

⭐ 一句话：**第 16 关那句「名单按地址排」，说的是【`set` 那一份】；
本关这个执行器手里拿的，是【`vector` 那一份】。** 两种容器给出的顺序**本来就可以不一样**
（第 16 关 §0.2(b) 那张三种容器的表就是为这儿准备的）。

⚠️ **但别急着下结论。** `EventsCBGExecutor` 是从 `rclcpp::Executor` **继承**下来的 ——
基类那份收集器**并没有被删掉**，还在它肚子里。
所以运行时**到底哪一份说了算**、`vector` 那份又是**谁在用它排班**，
**本关一个字都不写** —— 这正是 §0.5 实验 A 要量的东西。

#### (d) 新执行器多出来的**三样东西**

| 多出来的 | 出处 | 干什么用 |
|---|---|---|
| `scheduler`（`CBGScheduler`） | `events_cbg_executor.hpp:258` | **自己排班** —— 不再靠基类那个「每轮问一遍名单」的循环 |
| `timer_manager`（`TimerManager`） | `events_cbg_executor.hpp:336` | **自己管定时器**（谁到点了） |
| `number_of_threads_` + 自己的 `run(...)` | `events_cbg_executor.hpp:312` / `:243` | **自己开一池子手** |

⭐ 整份头文件里最能说明问题的是这**四行**（`events_cbg_executor.hpp:236-239`）：

```cpp
using rclcpp::Executor::execute_timer;         // 怎么【跑】一个定时器 —— 借基类的
using rclcpp::Executor::execute_subscription;  // 怎么【跑】一个订阅 —— 借基类的
using rclcpp::Executor::execute_service;       // 怎么【跑】一个服务 —— 借基类的
using rclcpp::Executor::execute_client;        // 怎么【跑】一个客户端 —— 借基类的
```

**翻译成人话：「『怎么跑一个』我借基类的；『挑哪一个来跑』我自己来。」**
⇒ 它换掉的正好是第 16 关那两个零件里的**②那一半**。

⚠️ 顺带一条**读来的**（`events_cbg_executor.hpp` 构造函数注释原文）：
线程数给 `0` 时 —— **"will use the number of cpu cores found (minimum of 2)"**
（用 CPU 的核数，**最少 2 条**）。这条是理论，本关数手时要用到。

#### (e) `--isolated` 是什么（本机没有它的 `.cpp`，只能从**二进制自己的名字**里读）

`component_container --help` 列的第二个词。本机的容器**只有编译好的二进制**，没有源码，
但二进制的符号表里明明白白写着两族名字：

```text
ComponentManager<...Executor>            ← 不隔离的那一版
ComponentManagerIsolated<SingleThreadedExecutor>
ComponentManagerIsolated<MultiThreadedExecutor>
ComponentManagerIsolated<EventsCBGExecutor>
```

（`Isolated` = **隔离**；`<...>` 里那个模板参数就是**执行器类型**。）

⭐ 读出来的那句：**隔离版 = 给每个组件配一个自己的执行器。**
（不隔离的那版：所有组件**共用一个**执行器。）

⚠️ **推出来的**（本关不写结论，留给实验）：既然每个组件各有各的执行器，
第 12 关那把「数手」的尺子**应该量得出差别** —— 差多少、怎么差，去量。

#### (f) 一个名字很像的**别人家的队列**（先立块牌子，防搞混）

`experimental/executors/events_executor/simple_events_queue.hpp` 里有个队列：

```cpp
std::queue<...> event_queue_;   // push 进【尾】、front() 从【头】取 ⇒ 先进先出
```

（`enqueue` / `dequeue` = 入队 / 出队；`std::queue` = **先进先出**的容器。）

⚠️ **这是另一个执行器（`EventsExecutor`）用的，不是本关 `events-cbg` 用的那一套**
（CBG 版用的是 `scheduler` + `RegisteredEntityCache`）。
写在这儿只是因为**名字太像** —— 别拿它当本关的证据。（这是第 16 关「三份名单」那次教训的延续。）

**尺子 ①（第 16 关那把）· 先上比例** —— 打开日志找**第一次**出现的那两行：

**谁在上面，谁就是「先上的那个」。** 先上比例 = 「`A` 先上」的轮数 ÷ 总轮数。

⚠️ 老规矩一字不改：**一轮的结果永远是 0 或者 1，一份日志里什么都读不出来** ⇒

| 装什么 | `Sleeper`，代码**一个字不改** |
| 唯一的差别 | 起容器那行：`--executor-type multi-threaded` → **`--executor-type events-cbg`** |
| 怎么做 | 起容器 → `load` → 看第一对 `读到` 两行 → **Ctrl+C 掉重开** → 下一轮（**10 轮**） |
| **先写预测** | **10 轮里，会有几轮是 `B` 先上？** 写成一个**数字** |
| **判据** | **先上比例** = `A` 先上的轮数 ÷ 10 |
| 对照组 | 第 16 关实测：`multi-threaded` 下是 **`0/17`**（17 轮 A 一次没先上） |

⚠️ 预测必须写成**数字**（第 15 关那条：**能算出来的东西才叫预期**）。
⚠️ **拿张纸记 10 行**：`第1轮 = B`、`第2轮 = A`……
⚠️ 每轮之间必须**重启进程**（第 16 关的纪律：**`Ctrl+C`，不是 `kill` / `timeout`** —— 那俩只杀外壳，会留孤儿伪造数据）。

#### 实验 B：**再加一个词 —— `--isolated`**

| | |
|---|---|
| 动的旋钮 | 🆕 **隔离**：`--executor-type events-cbg --isolated` |
| **先写预测** | 实验 A 那个比例，**加隔离之后变不变**？ |
| 顺带看 | 这一轮里，`--isolated` 该算「换手」还是「换名单」？ |

⭐ **A 和 B 之间只差一个词** —— 这就是本关的判据实验。

#### 实验 C（加练）：**数手**（第 12 关那把尺子）—— 一个 2×2 的表

|  | `--executor-type multi-threaded` | `--executor-type events-cbg` |
|---|---|---|
| **不加** `--isolated` | 第 12 关量过：**33** | ? |
| **加** `--isolated` | ? | ? |

**四格全填，尺子同上**：`ls /proc/<PID>/task | wc -l`。
⚠️ 一次只改**一个词**，别一次改两个。
⚠️ 数手要在**组件 load 完之后**数（容器刚起来时组件还没进去）。

## 2. 核心概念

### 2.1 「执行器」在本课出现过**两种**意思

| 关 | 说法 | 真实含义 | 换的是 |
|---|---|---|---|
| 第 12 关 | 「换容器 = 换执行器」 | `component_container` ↔ `component_container_mt` | **配置**：几只手的池子。**类没变** |
| **第 17 关** | 「换个执行器」 | `--executor-type events-cbg` | **类**：换一整台机器 |

⭐ 这就是本关能问出「归谁管」的前提：**以前只调档位，从没换过机器。**

### 2.2 三个实现，全是 `rclcpp::Executor` 的孩子

```text
rclcpp::Executor                        (executor.hpp:64 —— 基类)
├── SingleThreadedExecutor              --executor-type single-threaded（默认）
├── MultiThreadedExecutor               --executor-type multi-threaded（第 12–16 关）
└── EventsCBGExecutor                   --executor-type events-cbg      （本关 🆕）
```

⚠️ 基类里那一整套「收集实体 → 排序 → 逐个问通行证」的机器（`ExecutorEntitiesCollector`）
**在派生类里依然存在** —— 换实现**不等于**把旧的那套拆掉。所以「运行时到底哪一份说话」
必须**实验**，不能靠读。

### 2.3 ⭐ 两份名单，两个容器（本关的题眼）

| 名单 | 容器 | 天然顺序 | 谁在用 |
|---|---|---|---|
| 基类 `ExecutorEntitiesCollector` | `std::set` + `owner_less` | **地址从小到大** | 第 16 关那个 `multi-threaded` |
| `EventsCBGExecutor::added_callback_groups` | `std::vector` | **加入的先后** | 本关 |

**同一批对象，放进 `set` 和放进 `vector`，排出来的顺序本来就可以不一样** ——
第 16 关 §0.2(b) 那张表早就把三种容器的规矩列好了，这一关就是去用它。

### 2.4 新执行器多出来的三样 + 那两行 `using`

| 多出来的 | 出处 | 干什么 |
|---|---|---|
| `CBGScheduler` | `:258` | 自己排班 |
| `TimerManager` | `:336` | 自己管谁到点了 |
| 线程池（`number_of_threads_` + 自己的 `run`） | `:312` / `:243` | 自己开一池子手 |

```cpp
using rclcpp::Executor::execute_timer;         // 「怎么跑一个」—— 借基类的
using rclcpp::Executor::execute_subscription;  // 「怎么跑一个」—— 借基类的
// （一共四行，execute_service / execute_client 同款 —— `:236-239`）
```

**它换掉的正好是第 16 关那个「②从尾巴取」** —— 保留「跑」，换掉「挑」。

### 2.5 `--isolated` 换的是哪一格：**执行器 ↔ 组件**

本机没有它的 `.cpp`，但二进制的符号表写着 `ComponentManagerIsolated<...Executor>`
⇒ **隔离 = 每个组件配一个自己的执行器**。

§7 的数手表把它验证了：**不隔离时数字纹丝不动，隔离后每装一个组件就多出一整套手。**

```
不隔离：33 → 33 → 33          （大家共用一个执行器）
隔离  ：18 → 34 → 50          （18 是容器自己，每装 1 个 +16）
```

### 2.6 本关的答案（终版）

| 问题 | 答案 |
|---|---|
| 「从尾巴取」是谁的性质？ | **发名单的人**（执行器实现）。名单没动，换个实现，方向就反了 |
| 换完之后还是「确定」的吗？ | **不是**。`multi-threaded` 是 **20/20 一个方向**；`events-cbg` 变成 **A 34/50**，两个回调差 **0~210 µs** |
| `--isolated` 换哪一格？ | **执行器 ↔ 组件的关系**（每个组件一套自己的执行器 + 自己那一池子手），**不动组件内部**的顺序 |
| 判据还成立吗？ | **不成立** —— 「谁在上面」在 `events-cbg` 下会骗人（50 轮里 11 轮和**时间戳**打架）。**换成按时间戳数** |

⭐ 一句话：**「先上」的归属是【发名单的人】的，不是【名单】的。**
名单是**数据**，它不决定谁先上；谁先上取决于**谁在读它、从哪一头读**。

### 2.7 ⚠️ 本关**没有**解决的那个死结：换方向 vs 换名单

到这一步还剩一个说不清的地方，而且它**跟第 16 关那个死结是同一个形状**：

| | 猜想 A：**同一份名单，换个方向取** | 猜想 B：**换了一份名单**（`vector`，按创建顺序） |
|---|---|---|
| 主张 | 结构还是 `set`（地址升序），只是**从头**而不是从尾巴取 | 结构换成 `vector`，顺序 = **加入的先后** |
| 都能解释「A 常先上」吗？ | 能（A 地址最小） | 能（A 先加入） |
| 怎么分 | 得让「**地址顺序**」和「**加入顺序**」分岔 | 同左 |

⚠️ **在这一份代码里它们永远分不开** —— 因为 `A` **既是最小地址、又是最先创建的那个**
（第 16 关 §10 题 2 说「本关做不到」，本关**还是做不到**）。

## 7. 实测现象与结论 ⭐

### 7.0 前置：**第一批 10 轮作废了**（数据卫生，先记一笔）

第一次跑完 10 轮，结果是 `A 10 / B 0`。**但那一批不能要** —— 日志里冒出了 `[C]`：

```text
[sleeper]: A 住哪 = 0x761808164130      ← 这三行是第 16 关实验 D 加的量具
[sleeper]: B 住哪 = 0x761808164010
[sleeper]: C 住哪 = 0x761808164470
[sleeper]: [C] 第1拍 读到 shared=0      ← 第三个定时器还在！
```

而磁盘上的源码**只有两个定时器**。⇒ **`build/` 里那个 `.so` 是旧的**（第 16 关实验 D 那一版，
10-08 **21:34** 编的；源码 **21:37** 才被 `git checkout` 还原回来）。
**跑的不是基准版** ⇒ 它和第 16 关的 `0/17` 之间隔着**两个**差别（换执行器 **＋** 多一个定时器），
**违反「一档只动一个」⇒ 整批作废**。重新 `colcon build` 后重跑，才有下面的数。

### 7.1 表 ①：**先上比例**（尺子 = 时间戳）

| 起容器那一行 | 轮数 | `A` 先上 | `B` 先上 | 「公平硬币」撞出这种结果的概率 |
|---|---|---|---|---|
| `multi-threaded`（对照：第 16 关 17 轮 ＋ 今天 3 轮） | 20 | **0** | **20** | —— **一次都不翻** |
| `events-cbg`（实验 A） | 50 | **34** | 16 | **0.77%** |
| `events-cbg --isolated`（实验 B） | 20 | **17** | 3 | 0.13% |

⭐ **答案：换执行器 ⇒ 方向【反了】（`B` 从不翻 → `A` 占 2/3），而且【不再确定】（50 轮翻过 16 次）。**

### 7.2 表 ②：**数手**（尺子 = 进程线程数，实验 C）

| 起容器那一行 | 空容器 | 装 1 个组件 | 装 2 个组件 |
|---|---|---|---|
| `--executor-type multi-threaded` | 33 | 33 | 33 |
| `--executor-type multi-threaded --isolated` | **18** | **34** | **50** |
| `--executor-type events-cbg` | 36 | 36 | 36 |
| `--executor-type events-cbg --isolated` | **18** | **37** | **56** |

读法（第 12 关那笔账：底下 **17** 条是 DDS 的，**18 = 17 + 1 只手的单线程容器**）：

| | 不隔离 | 隔离 |
|---|---|---|
| 组件的执行器 | **大家共用一个**（数字不随组件数变） | **每个组件一套自己的**（每装 1 个 **+16** / **+19**） |
| 容器节点自己的手 | 和执行器同池 | 单独 1 只（空容器 18） ⇒ 也就是为什么**空容器**那格是 18 而不是 33 |

⭐ **一句话：`--isolated` 换的是【执行器 ↔ 组件的关系】，顺带把【手数】变成了「组件数 × 每套手数」。**

⚠️ **顺带量出来的一个数，本关解释不了**：`events-cbg` 默认给 **19** 条手，`multi-threaded` 默认给 **16** 条。
上头那条源码注释说「默认用 CPU 核数（最少 2）」—— 这台机器 16 核，多出来的 **3 条**是干什么的，
**不知道，没量**（已进 §10 加练）。

### 7.3 表 ③：**`--isolated` 不改【先上】**（实验 B）

`events-cbg` 50 轮 → `A 34/50`；加上 `--isolated` 20 轮 → `A 17/20`。
**比例没变**，符合预期：隔离管的是**组件之间**，本关只有 1 个组件。

### 7.4 ⚠️⚠️ 本关最值钱的一条：**「谁在上面」会骗人**

50 轮里 **11 轮**（实验 B 里 3/20）出现 **行序** 和 **时间戳** 打架：

```text
[INFO] [1791542505.003923541] [sleeper]: [B] 第1拍 读到 shared=0   ← 排在【上】面
[INFO] [1791542505.003923088] [sleeper]: [A] 第1拍 读到 shared=0   ← 时间戳更【早】453 ns
```

⇒ **日志的行序本身也是抢出来的**（两个线程都在往同一个输出器里写）。
⇒ 尺子必须**从「行序」换成「时间戳」**。

⭐ 这是「**判据会失效**」的**第三次**，但**失效的原因**和前面两次都不同：

| 关 | 判据怎么失效的 | 解法 |
|---|---|---|
| 第 14 关 | 一个现象**两个原因**（锁拦的 / 手拦的） | 换观测量：**间距** |
| 第 15 关 | `④ = 1/1` **两种来源**（真保护 / 把写者饿死） | **分开数 A / B** |
| 第 16 关 | **一轮里根本没有信息** | 换**做法**：重跑 |
| **第 17 关** | **观测量自己也会被抢**（行序 ≠ 发生顺序） | **换一个观测量：时间戳** |

### 7.5 间距：两组的**手感**完全不一样

| 组 | 两条 `读到` 的间距 | 形状 |
|---|---|---|
| `multi-threaded`（对照） | 160.7 / 162.8 / 398.4 µs | **一个接一个**：上一个被捞走，过 160 µs 才轮到下一个 |
| `events-cbg`（实验 A） | 0.00 ~ 210.3 µs，**中位 12.6** | **两只手同时捞**：几乎同一瞬间 |
| `events-cbg --isolated`（实验 B） | 0.00 ~ 173.3 µs，**中位 3.3** | 同上 |

⭐ 对照组的间距**比实验组大一个数量级** —— 这就是「确定地一个接一个」和「抢」在手感上的区别。

### 7.7 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **「怎么走名单」是【发名单的人】的性质** | 名单一个字没改，只换执行器实现 ⇒ 方向从 `B` 翻到 `A` |
| 2 | **它从「确定」变成了「抢」** | 对照 20/20 一次不翻 ↔ 实验 34/50；间距 160 µs ↔ 12.6 µs |
| 3 | **`--isolated` = 每个组件一套自己的执行器**（换的是「执行器 ↔ 组件」） | 不隔离 33/33/33 ↔ 隔离 18/34/50 |

### 坑 1（本关）· `git checkout` 还原了源码，**但没人重新 build**

**现场**：第一次实验跑出 `A 10 / B 0`，看着像完美答案 —— 直到日志里冒出
`[C] 第1拍 读到` 和 `C 住哪 = 0x...`。

**证据链**：

| 东西 | 时间戳 | 内容 |
|---|---|---|
| `src/.../sleeper_component.cpp` | 10-08 **21:37** | **干净基准**（2 个定时器，`grep -c "住哪\|tick_c\|count_c"` = **0**） |
| `build/.../libsleeper_component.so` | 10-08 **21:34** | **3 分钟前的**：3 个定时器 + `%p` 量具 |
| `strings` 那个 `.so` | —— | `[C]` **在**；`strings` 源码编译后的新 `.so` | `[C]` **不在** |

**根因**：第 16 关收工把源码 `git checkout` 回去了，**但没有重新 `colcon build`** ——
`install/lib/libsleeper_component.so` 是个软链，指向 `build/` 里那个**旧的**。

**⭐ 这是「`.so` 不热重载」的【镜像】**：

| 关 | 形状 | 结果 |
|---|---|---|
| 第 13 / 14 关 | **改了源码、重新 build 了，但容器开着** | 跑的**还是旧的那个** `.so` |
| **第 17 关** | **把源码改回去了，但没重新 build** | 跑的**还是旧的那个** `.so` |

**共同的一句话：`.so` 只认【最后一次 build】，不认【磁盘上现在是什么】。**

**防它的一招（本关新立）**：**跑之前先看 `.so` 的时间戳**——

```bash
ls -l --time-style=+%m-%d_%H:%M build/hello_ros_cpp/libsleeper_component.so \
      src/hello_ros_cpp/src/sleeper_component.cpp
```

**`.so` 比源码旧 ⇒ 先 build，别跑。**（和第 15 关那条「改完先 `grep -n` 看一眼」是一家：
**先验收旋钮，再读结果**。）

### 坑 2（本关）· 行序 ≠ 时间戳：**行序会骗人**

见 §7.4。50 轮里 11 轮打架。**日志是多个线程抢着往一个输出器里写的** ——
**「谁在上面」只证明「谁的 write 先拿到锁」，不证明「谁先发生」。**
⇒ 本关起，数顺序**一律用时间戳**。

### 坑 3（本关）· `set -u` 撞上 ROS 的 `setup.bash`

写探针时在脚本里 `set -u` 然后 `source /opt/ros/lyrical/setup.bash`，当场报：

```text
/opt/ros/lyrical/setup.bash: 行 8: AMENT_TRACE_SETUP_FILES: 未绑定的变量
```

`setup.bash` 里有**未绑定的变量**（它自己会用默认值兜）。**脚本里要 `set -u`，
就把它夹在 source 的两边**：

```bash
set +u
source /opt/ros/lyrical/setup.bash
source ~/ros2_learn_ws/install/setup.bash
set -u
```

### 坑 4（本关，轻）· 「公平硬币」不是随口说的

`events-cbg` 第一次只跑 10 轮，得到 `A 7 / B 3`。**这看着像「一半一半」，但它证明不了任何事** ——
公平硬币掷 10 次出现「至少 7 次正面」的概率是 **~17%**，太常见。
**必须先算，再决定要不要接着跑。**（第 16 关「6 次够不够是算的」那一课的复用。）
